# Decision notes: what I built, what I tried, what it cost

Sonido is a set of 36 audio effects. The same Rust source runs as CLAP and VST3 plugins, in a browser node editor, and as firmware on an Electrosmith Daisy Seed (STM32H750, Cortex-M7 at 480 MHz) inside a Hothouse pedal. I wrote it alone, between January and October 2026.

These notes present the project as a series of decisions. Each section covers one algorithm or system, in the same order: what I built, what I tried first, what it cost, and what it still doesn't do. Every number comes from a file in this repository, and the section names the file. Most of the numbers are regenerated by a script or enforced by a test.

**The constraint behind most of these decisions.** On a laptop CPU (an i5-6300U), every effect runs in under 3.5% of one core, so the desktop never forces a tradeoff. On the pedal, the clock gives each sample 10,000 cycles, audio moves in 32-sample blocks of 320,000 cycles, and the main reverb alone uses 62% of a block in its worst case. Most of the choices below were made for the pedal and then kept on the desktop, because the point of the project is one codebase.

## 1. One kernel, three targets

**What I built.** Every effect is three layers. `XxxParams` is a plain struct of parameters in user units (dB, ms, %). `XxxKernel` is the DSP: `process_stereo(left, right, &params)`. It holds only DSP state (filter memory, delay lines, oscillator phases), allocates nothing while processing, and reads its parameters by reference on every call. `Adapter<K, SmoothedPolicy>` owns per-parameter smoothing (5 to 50 ms ramps, chosen per parameter) and the dynamic interface hosts need. A single registry builds every effect this way for the plugins, the editor and the pedal. The pedal plays every rig through `PatchPlayer`, the same runtime as the graph-player plugin. Because the parameter struct is also the preset format, morphing between two presets is `lerp()` on two structs. Sources: [ADR-028](../DESIGN_DECISIONS.md#adr-028-kernel-architecture--dspparameter-separation), [KERNEL_ARCHITECTURE.md](../KERNEL_ARCHITECTURE.md).

**What I tried first.** The first version had effects that owned their own smoothers, behind a classic `Effect` trait. Plugin hosts, preset recall and morphing all needed the parameters outside the DSP, so in March 2026 I moved 19 effects to kernels and deleted the old structs. For the pedal I then went one step further and ran kernels without software smoothing. I wrote that down as a rule ([ADR-029](../DESIGN_DECISIONS.md#adr-029-hardware-serves-the-kernel--embedded-design-principle), rule 5): the Hothouse's pots are filtered in hardware, so smoothing them again in software seemed like wasted cycles. Without the adapter's smoothing, though, the pedal applied each control change as a step at its 100 Hz control rate, while a plugin ramped the same change over 5 to 50 ms. In October I reversed the rule. The pedal now builds every effect with the same smoothed adapter as the plugins, so a rig sounds the same in a DAW and on the pedal.

**What it cost.** On the Cortex-M7, the smoothed path costs 2,000 to 13,000 cycles per effect per block more than the bare kernel, which is 0.6% to 4% of the budget for each effect ([BENCHMARKS.md](../BENCHMARKS.md#cortex-m7-measured-on-a-daisy-seed)). Smoothing also caused one new bug. A freshly loaded rig smoothed every parameter from its default toward its stored value, which recalculated every coefficient on every sample at once. The first block peaked at 116% of the budget. A loaded rig now snaps its parameters to their values (`Effect::snap_params`).

**What it still doesn't do.** The pedal and the plugin run the same source compiled for different targets, not the same binary. The input and output differ too: the pedal sums its input to mono and clips at 0 dBFS on the way to its codec. A pedal and a plugin set to the same values can still sound different at the edges.

## 2. Aliasing: ADAA instead of oversampling

**What I built.** The distortion (four curves: tanh soft clip, hard clip, foldback, asymmetric), the amp's two gain stages and the tape's asymmetric exponential saturator all use first-order antiderivative anti-aliasing (ADAA; Parker et al., DAFx-2016). Instead of `f(x[n])`, each sample outputs `(F(x[n]) − F(x[n−1])) / (x[n] − x[n−1])`, where `F` is the curve's antiderivative (`ln cosh x` for tanh). That is the average of the curve over the interval between two samples, which acts as a continuous-time box filter on the nonlinearity's output. An aliasing test fails the distortion, preamp, amp or tape kernel if inharmonic energy exceeds 5% of the total (`crates/sonido-effects/tests/aliasing.rs`).

Measured on a 1 kHz tone at 48 kHz ([DSP_MEASUREMENTS.md](../DSP_MEASUREMENTS.md)): THD tracks drive, from 13.19% at 10 dB to 43.20% at 40 dB. At 30 dB of drive the soft clip's third harmonic is at −9.6 dB relative to the fundamental and the fifth at −14.5 dB, and every even harmonic stays below −114 dB, as an odd-symmetric curve should.

**What I tried first.** Oversampling. `Oversampled<N>` upsamples with a polyphase Blackman-Harris windowed sinc (8 taps per phase) and downsamples with a 48-tap Kaiser-windowed FIR (β = 8). I raised that from 16 taps after measuring only about 40 dB of stopband attenuation. It now clears 80 dB, at the price of 27 samples of latency ([ADR-003](../DESIGN_DECISIONS.md#adr-003-const-generic-oversampling)). On the desktop, oversampling the distortion costs 2.11× at 2×, 3.86× at 4×, and 7.50× at 8×. On the pedal, the distortion's worst block is 12.5% of the budget. If the desktop ratio held there, 4× would take it close to half a block, and nothing else heavy would fit beside it; the reverb alone needs 62%. So no shipping path oversamples. The wrapper is still in the code for offline use and for the tests.

**What it cost.** Precision, in two places.

The first is numerical. The ADAA quotient divides the difference of two antiderivative values by a small input difference, so any rounding error in `F` is amplified when consecutive samples are close together. That is exactly what a quiet signal looks like. Until October, quiet input came out only 16–27 dB above the antiderivative's own rounding noise, which was audible as grit on the distortion, amp, preamp and tape on every target. Two changes fixed it. `F` is now exactly zero at the origin: a seven-term Taylor series for `ln cosh x` below |x| = 0.5, and an overflow-safe form above that. And the cutoff for falling back to the midpoint `f((x[n] + x[n−1]) / 2)` is now relative, `1e-3 · (1 + max|x|)`, where it used to be an absolute `1e-5`. Quiet input now sits at least 93 dB above rounding noise (`crates/sonido-core/src/adaa.rs`, `soft_clip_ad` in `crates/sonido-core/src/math.rs`).

The second is in the frequency response. In the linear part of any of these curves, first-order ADAA reduces to the average of two neighboring samples, a lowpass of `cos(πf/fs)`. At 48 kHz that is −0.5 dB at 5 kHz, −2.0 dB at 10 kHz and −11.7 dB at 20 kHz (computed from the formula, not measured). The kernel doesn't compensate for it; the distortion's tone control comes after the waveshaper.

**What it still doesn't do.** The curve doesn't change shape with playing level. The distortion's `dynamics` control runs an envelope follower that lowers the drive by up to 14 dB as you play quieter, so rolling back the guitar's volume does clean it up. But it does that by feeding a quieter signal into the same fixed curve, without the knee softening or the harmonic balance shifting the way many analog circuits do. Level-dependent waveshaping is on the [roadmap](../ROADMAP.md#dynamic-waveshaper-response). I also use only first-order ADAA. Second-order would suppress aliasing further, at the cost of a second antiderivative and a wider ill-conditioned region.

## 3. The main reverb: from Freeverb to an FDN

**What I built.** An 8-line feedback delay network (Jot and Chaigne 1991). Each line's output is mixed with every other line's through an 8×8 Hadamard matrix before feeding back. I implement the matrix as a fast Walsh-Hadamard butterfly: 24 additions and subtractions, then one scale by 1/√8, so the mixing preserves energy. The line lengths are Freeverb's comb tunings (1116 to 1617 samples at 44.1 kHz, rescaled to the actual sample rate). Each line has a one-pole lowpass in its feedback path, with the damping control mapped logarithmically from 20 kHz down to 200 Hz. Feedback comes from Freeverb's room constants. A 14-tap early-reflection delay with prime spacing runs alongside the network. Four modulated allpasses per channel diffuse the output, and the right channel's tunings are offset by 23 samples. The left output averages the even lines and the right the odd lines, so the channels decorrelate without any panning. At the defaults, the measured RT60 is 3.38 s (Schroeder backward integration, fit correlation 0.997). Source: `crates/sonido-effects/src/kernels/reverb.rs`.

Each line's read position is swept by its own sine LFO, at one of eight rates from 0.3 to 1.3 Hz, all 0.3 ms deep. A delay swept sinusoidally detunes its signal by at most 2π · rate · depth, which here works out to about 1 cent on the slowest line and 4 cents on the fastest (computed from the constants). The rates all differ so that the lines never move together.

**What I tried first.** Freeverb as published: eight parallel combs into four series allpasses, with a separate tank for each channel ([ADR-009](../DESIGN_DECISIONS.md#adr-009-separate-reverb-tanks-for-stereo)). Its wet level rose with decay, and I went through two compensations: first a quadratic, `1 − x² · 0.88`, then `√(1 − g)`. For the single-comb effects (delay, flanger, phaser), `√(1 − g)` is provably not enough. A comb's peak gain at resonance is `1/(1 − g)`, so with `√(1 − g)` compensation the output at mix `m` is `(1 − m) + m/√(1 − g)`, which is above 1 for every `g > 0`. Those effects now use the exact `(1 − g)` ([ADR-019](../DESIGN_DECISIONS.md#adr-019-generalized-feedback-compensation)). The reverb keeps `√(1 − g)`, because exact compensation at hall feedback (`g` ≈ 0.98) would leave the wet signal at 0.02, which is −34 dB. In February I replaced the comb bank with the FDN, keeping Freeverb's tunings and room constants.

**What it cost.** CPU, more than anything else in the project. Before I had turned on the M7's caches or optimized anything, the reverb took 1,191,763 cycles per block, 372% of the budget. Turning on the caches, compiling for the M7 specifically, using a fast sine approximation in place of `libm`'s, and switching the modulated lines from cubic to linear interpolation brought it to 159,033 cycles. Linear interpolation attenuates high frequencies by an amount that depends on the fractional delay, so the modulated lines lose a little top end that cubic interpolation would keep. At the default damping, the loop's one-pole lowpass (near 2.5 kHz) removes far more.

Today, with the early reflections and modulated diffusion added, the reverb's worst block is 197,300 cycles (61.7%), the heaviest effect the pedal's jam offers. That sets the shape of the pedal: one reverb per rig. Two reverbs measured 123% on average on an earlier firmware, with every single callback over budget. Next to the reverb and a distortion, only the filter, ring modulator or bitcrusher fit.

The reverb also produced the worst bug in the browser demo. A sustained tone into a high-feedback setting could drive a delay line to infinity or NaN, and the bad value stayed in the line, so stopping and restarting playback never recovered. The audio engine now checks every block: if the output is not finite, it flushes the graph's state and outputs silence for that block.

**What it still doesn't do.** The FDN and the early reflections are fed a mono sum (the predelay before them is stereo). Decay is a percentage passed through Freeverb's constants, not a time in seconds; the plate and spring do take seconds (next section). There is no freeze. And I have not compared sine modulation against randomized modulation, by ear or by measurement.

## 4. Allpasses, plates and springs

**What I built.** A plate (after Dattorro 1997) and a spring (after Välimäki et al., DAFx-06). In both, decay is an RT60 in seconds. The gain per trip around the loop is `10^(−3 · L / (T60 · fs))`, where `L` is the loop length in samples, so the tail falls 60 dB in the time on the knob whatever the size or tension.

The plate sums its input to mono, band-limits it, pre-delays it, and diffuses it through four input allpasses. It then feeds a tank of two cross-coupled halves, each a modulated allpass, a delay and a damping filter. Dattorro-style output taps add a tap from one half and subtract a tap from the other, so the two channels share the tail's energy but not its waveform.

The spring disperses its signal through six Schroeder allpasses in series. The tension control sets their lengths, from twice the base length (loose) down to half (tight), and a feedback delay closes the loop. A soft limiter inside the loop guards against runaway, and the output is mono. Sources: `crates/sonido-effects/src/kernels/plate_reverb.rs`, `spring_reverb.rs`.

**What I tried first.** My allpasses used Freeverb's shortcut, `y = −x + v[n−D]`. That is not a true allpass. Its response is `(−1 + (1+g)·z⁻ᴰ) / (1 − g·z⁻ᴰ)`, with up to about 2× gain at the frequencies where `z⁻ᴰ = −1`, even at `g = 0`. Freeverb gets away with it because its allpasses come after the reverb, where the error is only a coloration. My delay's diffusion and my plate's tank put allpasses inside a feedback loop, where that extra gain pushed the loop gain past 1 and the effect ran away. Since October every allpass in Sonido is a true Schroeder allpass, `(−g + z⁻ᴰ) / (1 − g·z⁻ᴰ)`, and a test checks that its gain is within 1% of unity at frequencies from 100 Hz to 9 kHz (`crates/sonido-core/src/allpass.rs`).

The decay controls had a worse bug. Both reverbs computed the gain that brings a signal down 60 dB over the decay time when applied once per *sample*, then applied it once per trip around the loop. That gain is about 0.99999 for any decay, so the clamp that guarded against runaway fixed the plate's feedback at 0.98 and the spring's at 0.97, whatever the knob said. Until October, both Decay controls did nothing. Until the same month, the spring's tension control also didn't change the allpass lengths it is documented to change.

**What it cost.** Worst blocks of 22.7% for the plate and 9.2% for the spring. Before the level work in section 6, the plate played 7.5 dB below the dry signal when fully wet, so turning its mix up made it quieter.

**What it still doesn't do.** The spring is mono, and it models dispersion and decay, not the spring's mechanical nonlinearity; its "drip" control is a soft clipper at the input.

## 5. Harmonic Habitat: a reverb tuned to the note

**What I built.** An FDN tail, like the main reverb's, colored by a bank of six peaking filters per channel. The filters are tuned to the input's pitch times one of four sets of ratios: Neutral (1, 1.5, 2, 2.25, 3, 4), Major (1, 5/4, 3/2, 2, 5/2, 3), Minor (1, 6/5, 3/2, 2, 12/5, 3) and Open Fifth (1, 1.5, 2, 3, 4, 6). A zero-crossing tracker estimates the fundamental between 55 and 1200 Hz. The coloring's strength is Harmonicity × Tracking, scaled from 25% up to 100% by how confident the tracker is, and a Memory control sets how slowly the tuning follows a new note (a time constant from 35 ms to about 1.2 s). With Tracking at 0 the filters are bypassed, and the effect is a plain FDN reverb. Source: `crates/sonido-effects/src/kernels/harmonic_habitat.rs`.

**What it cost.** A worst block of 113,621 cycles, 35.5% of the budget, so on the pedal it can't share a rig with the main reverb. Before the level work, it played 10.4 dB below the dry signal when fully wet, the largest gap of any effect.

**What it still doesn't do.** It follows one fundamental. A zero-crossing tracker is cheap, but chords and noisy input lower its confidence, and the coloring falls back toward a quarter of its set strength. There is no polyphonic tracking.

## 6. Level: measured, not chosen

**What I built.** One rule for every effect ([ADR-031](../DESIGN_DECISIONS.md#adr-031-one-measured-level-contract)). At its defaults, an effect plays at the loudness of its input, and its mix control doesn't change that loudness. Each kernel declares a `Level`: a trim, plus the measured correlation ρ between its wet signal and its dry input. Kernels with a mix control blend with the gains `cos(πm/2)` and `sin(πm/2)`, normalized by `1/√(1 + ρ · sin(πm))`. Two signals with correlation ρ at gains `a` and `b` sum to a power of `a² + b² + 2ρab`, so one law covers every kind of wet signal. For an uncorrelated wet (ρ = 0: reverbs, echoes) it is the plain constant-power crossfade. For a fully correlated wet (ρ = 1: saturation) it keeps amplitude like a linear crossfade. Partly cancelling wets (ρ < 0: a vibrato's comb) get a boost.

The trims are measured, never typed in by hand. A calibration program plays a synthetic strummed guitar through every effect and writes `crates/sonido-effects/src/calibration.rs`. The guitar peaks at −20 dBFS, the median I measured from a humbucker into the Hothouse's converter. The program measures integrated loudness to ITU-R BS.1770-4, fully wet for effects with a mix control and at the defaults for the rest. A test fails if any effect is more than 0.5 dB from the dry loudness, or more than 1.5 dB at 0, 25, 50 or 75% mix (`crates/sonido-effects/tests/level_contract.rs`). The factory rigs get master trims the same way.

**What I tried first.** Hand-set output defaults for each effect. One example is the tape's −6 dB, which offsets its drive ([ADR-017](../DESIGN_DECISIONS.md#adr-017-shared-dsp-vocabulary-and-gain-staging)). Others were the feedback compensations in section 3, and a linear crossfade for mixing. None of it held up. A linear crossfade of an uncorrelated wet loses 3 dB at 50% mix, and a constant-power crossfade of a correlated wet gains 3 dB. Every DSP change silently moved levels that nothing re-checked. Before the change, the plate fully wet was 7.5 dB under the dry signal and Harmonic Habitat 10.4 dB under.

**What it cost.** Three things:

- **Recalibration.** Any change to a kernel's sound or defaults means re-running the calibration, and the test fails until I do. The golden reference files have to be regenerated too, because the trim is part of the output.
- **One reference level.** The calibration holds for the reference guitar. A saturating effect fed a much hotter or quieter signal will measure differently.
- **Approximate math.** The mix law runs on every sample of every effect. `libm`'s `sqrtf` is a software routine on the Cortex-M7, so the law uses no transcendental functions at all: a polynomial quarter-sine accurate to 6 × 10⁻⁴, and a bit-trick inverse square root accurate to 5 ppm (`crates/sonido-core/src/level.rs`).

The sine law has a finite slope at both ends of the knob. The first few degrees of a mix knob fade the wet signal in, where a `√m` law would jump straight to −20 dB.

**Why it matters on a pedal.** The pedal's jam lets you swap effects mid-song, and the knobs at noon select the defaults. Any level mismatch between effects is a volume jump in the middle of a song.

## 7. Knobs: noon is the default

**What I built.** Each parameter's descriptor holds its full range and a default. The default is the voiced sweet spot, and a pedal knob at 12 o'clock selects exactly that default. The left half of the knob's travel maps the minimum to the default, and the right half maps the default to the maximum. Each half follows the parameter's own scale (linear, logarithmic or power). Stepped parameters split their options around the default the same way. A pedal at noon and a freshly opened plugin therefore start identical. Sources: [ADR-030](../DESIGN_DECISIONS.md#adr-030-noon-mapping-belongs-in-the-embedded-layer), `crates/sonido-platform/src/param_map.rs`.

**What I tried first.** Two other approaches, each in use for a while.

1. **Narrower ranges.** I narrowed each descriptor's range so that its midpoint landed on the sweet spot. That made noon work on the pedal, but every plugin, the editor and the CLI lost the rest of the range. I reverted it.
2. **A table of pedal sweet spots** (March 15 to October 22). The pedal kept its own noon values, separate from the defaults. For example, mix was 50% at noon on the pedal and 100% by default in the plugins, so the pedal at noon and a fresh plugin sounded different. I deleted the table and re-voiced the defaults to be the sweet spots.

Commercial pedals are the precedent for the final design. They keep the circuit's full range and bias the knob's response with the taper of the pot.

**What it cost.** A parameter voiced at the end of its range has a lopsided knob. The distortion's mix defaults to 100%, so on the pedal its whole range sits in the left half of the travel, and the right half holds at 100%. Changing a default now moves three things at once: the pedal's noon, the plugin's initial state, and the level calibration. On the pedal, three knobs also have floors that the plugins don't: delay time starts at 30 ms (below that it sounds like comb filtering), filter cutoff at 150 Hz, and bitcrusher depth at 5 bits. Tests run the mapping over every writable parameter of every effect, and they hold each jam effect within 1.5 dB of the dry guitar with every knob at noon.

## 8. CPU: budgeting by measured worst blocks

**What I built.** A benchmark firmware runs on the Seed, loaded over SWD. It times every effect for 8 warm-up blocks and then 128 measured 32-sample blocks with the M7's DWT cycle counter. It runs two passes: the bare kernel, and the effect exactly as a rig plays it (registry-built, smoothed, with the pedal's control tick). A script turns the log into the cycle table (`crates/sonido-platform/src/cycle_table.rs`), rounding each rig-path worst block up to the next 1,000 cycles. The rule: a rig runs if its effects' worst blocks, plus 400 cycles per node, add up to no more than 80% of the 320,000-cycle block. The editor warns past 70%. The same function decides in the editor, in the CLI, and on the pedal, both before it loads a rig sent over USB and before it accepts an effect picked with a knob.

The rule checks out against the whole pedal. Distortion into reverb into ring modulator is estimated at 79.4% under the rule. Measured in a Hothouse with a guitar, it ran at 74.7% mean and 84–85% at its slowest callbacks, with no block over budget ([EMBEDDED.md](../EMBEDDED.md#chain-configurations)).

**What I tried first.** Estimating instead of measuring. I took desktop nanoseconds per sample × 25, which is the clock ratio (3.0 / 0.48) times an assumed 4× architecture penalty. Once I had measured all 36 effects, the estimate's median error was +14%, and 28 of 36 fell within its claimed ±50%. All eight misses were overestimates, five of them by 1.7 to 3.1×: the cabinet, drone, time stretch, texture and tuner. Those kernels do periodic, grain-based or convolution work, and the desktop timing captured it badly. The first measured runs also caught problems the estimate could never have shown:

- **The tuner.** It ran its whole YIN analysis inside one block: 9,166,077 cycles, 29× the budget, which on the pedal meant a dropout every 43 ms. It now spreads the analysis over the blocks between updates, and its worst block is 63.7%.
- **The rig loader.** Building a rig took up to 12 ms against about 0.6 ms of slack, because audio and rig loading shared one cooperative executor. Every rig change dropped audio three or four times. The audio task now runs on its own interrupt-priority executor and interrupts everything else.
- **The cabinet.** It rebuilt its impulse response in its first audio block: 12,288 software sine and cosine calls, about 4 ms. It now keeps the response it was built with.

**What it cost.** The 20% margin refuses some rigs that might have worked. On the previous firmware, which ran the kernels without smoothing and with an older soft clipper, distortion into reverb into delay ran at 80.3% mean with a highest peak of 89.7% and no block over budget. Under the current rule it estimates at 86%, and the pedal refuses it. The measurements are also manual. No CI runner can repeat them, so if I change a kernel, its pedal cost is stale until I re-run the benchmark. A rebuild alone moves an unchanged effect by up to ±8% through code layout, which the margin absorbs.

## 9. Controls for a pedal without a screen

**What I built.** One rule for the controls, the same in every rig and mode ([ADR-032](../DESIGN_DECISIONS.md#adr-032-one-control-rule-for-the-pedal)).

- **Footswitches.** The left one taps on and off; bypass is a 5 ms crossfade to dry while the rig keeps running. The right one taps tempo, or glides between sound A and sound B when the middle toggle is in its middle position. Holding either for 0.4 s changes rig, and the change happens while the switch is still held.
- **Middle toggle.** Up is A, middle is morph, down is B.
- **Knobs.** The top row is levels, and the top-right knob is always a volume. The bottom row holds the three controls that shape the sound most.
- **LEDs.** Each LED shows what the footswitch below it does.

The rule lives in one Rust module (`crates/sonido-patch/src/controls.rs`). The firmware's control loop calls it, and the same module draws the illustrated guide that `sonido pedal controls` opens, so the guide can't drift from the pedal.

**What I tried first.** Modes. The first pedal firmware (March) had three: one to browse effects into slots, one to capture sounds A and B, and one to morph between them. Later versions gave the footswitches different jobs depending on the rig and the toggle position. Other gestures I tried and removed:

- **Footswitch scrolling.** Tapping scrolled through effects. That built every effect on the way, and it made the switches modal.
- **A bootloader hold.** Holding both footswitches restarted into the bootloader for firmware updates. I raised the hold from 1.5 s to 3 s after a bypass stomp rebooted the pedal mid-play, then removed it. The bootloader is now a power-on gesture or a USB request.
- **Soft takeover.** A knob stayed locked until it reached the stored value. Without a screen, a locked knob looked dead. Now a knob takes over once it moves 2% of its travel.

**What it cost.** Tap tempo isn't available while the middle toggle is in the morph position, because the right footswitch glides there. A rig change costs a 0.4 s hold. An effect picked with a knob loads only after the knob has rested for 0.3 s, so sweeping past effects doesn't build each one. And the jam offers 8 of the 36 effects.

## 10. Plugins: CLAP first, one bundle

**What I built.** One `sonido.clap` bundle with 37 plugins: the 36 effects and a graph player that runs a whole rig. Every plugin has a stable ID (`com.sonido.<effect>`). For VST3, a `sonido.vst3` shim from [clap-wrapper](https://github.com/free-audio/clap-wrapper) finds the CLAP at load time and hosts it, so the DSP and the UI exist only once. Every plugin draws the same cabinet UI, with a live scope of its own input and output.

**What I tried first.**

- **nih-plug.** I considered nih-plug, a Rust plugin framework. It would have replaced my parameter system, so I built on clack, a lower-level CLAP binding, instead ([ADR-024](../DESIGN_DECISIONS.md#adr-024-clap-plugin-architecture)).
- **egui-baseview.** I tried this crate for the GUI. It was pinned to an older version of egui, and its render loop conflicted with the state the plugin shares between threads, so I wrote my own bridge on `baseview` and `egui_glow`.
- **One file per effect.** The first plugins shipped as one `.clap` file per effect, 19 files at the time. I replaced them with the single bundle; the IDs stayed the same, so saved projects still load.
- **Native VST3.** A native VST3 adapter in Rust would remove the C++ build, but it would mean maintaining a second plugin-format adapter beside the CLAP one. I went with the shim instead.

**What it cost.** The VST3 shim is only a loader: it works only next to its matching `.clap`, and building it needs a C++ toolchain and the VST3 SDK. Steinberg's validator passed the shims 47/47 when I ran it once by hand, but no CI job runs it. The CLAP plugins are checked by clap-validator 0.3.2 in a manually triggered CI workflow.

## 11. How I check it

The tree has 1,954 `#[test]` functions. The ones that matter most for the decisions above:

- **Golden files.** The output of 32 of the 36 effects is compared against checked-in reference files. A test fails on a mean squared error above 10⁻⁶, a signal-to-noise ratio below 60 dB, or a spectral correlation under 0.9999. Changing the biquads from Direct Form I to Transposed Direct Form II meant regenerating 44 of these files.
- **The aliasing suite** for the ADAA kernels (section 2).
- **The level contract** for every effect, and the noon-loudness check for the jam (sections 6 and 7).
- **Default parity.** Every kernel's default parameters must equal its descriptor's defaults, the values every target starts from.
- **Property tests.** Every effect is pushed through random parameter sets and must produce finite, bounded output.

CI runs formatting, clippy with warnings denied, and the test suite on Ubuntu, macOS and Windows. It also builds the browser editor and builds, lints and size-checks the pedal firmware. What CI doesn't do is run anything on the pedal itself. I test the hardware by flashing it and playing, and the pedal's performance numbers are measured by hand. Details: [README.md](../../README.md#testing), [TESTING.md](../TESTING.md).

## 12. What it does not do

- **No oversampling on any shipping path.** ADAA handles aliasing, and the aliasing suite measures only four kernels.
- **No automatic gain control.** Levels are measured offline and fixed, for the CPU budget.
- **No 64-bit floats.** The M7's FPU is single-precision only.
- **No level-dependent waveshaping yet.** Drive follows playing level; the shape of the curve does not.
- **No phase vocoder.** The pitch shifter is granular (two or four Hann-windowed grains) and has no formant preservation, and there is no harmonizer.
- **No measured cabinets.** The three cabinet IRs are generated as exponentially decaying filtered noise and convolved directly over 256 samples. You can't load your own IR yet.
- **No MIDI and no expression input.** Library code exists for both; nothing is wired to a parameter.
- **A mono pedal.** It sums its input to mono, and the spring reverb is mono throughout.
- **Not a finished product.** The API is unstable, and nothing is published to crates.io.

The [overview](README.md) lists these alongside what the project does. The [build log](build-log.md) tells the hardware side of the same story.
